## 1. Cross-tenant id-lookup sweep

### Method

Automated regex scan of every `.py` file under `backend/` (excluding `tests/`,
`alembic`/`versions`) for `text()` calls whose SQL body matches `WHERE <x>.id = `,
`WHERE <x>_id = :param`, `UPDATE ... WHERE id =`, or `DELETE ... WHERE id =` with no
`tenant_id` anywhere in the same string. 90 candidates at `2570460`. Each was read in
its calling context to determine the id's source and whether a prior tenant-scoped
check protects it in the same request. The five branches introduce **zero** new
candidates — their diffs are migrations/grants, Celery partition DDL (not tenant-row
data), SA-bootstrap code, a docstring correction, and Markdown-only translations.

### Root cause of #1–#3 (the severe ones)

`tenant-service/dependencies.py` defines **two** DB-session dependencies:
`get_db_session` (generic — sets RLS context to the caller's *own* tenant, no
path-vs-caller comparison) and `get_db_session_for_tenant` (explicitly documented
as *"the single enforcement point for cross-tenant isolation in the tenant-service
— every `{tenant_id}` route must use this dependency"*; it 403s with
`TENANT_ACCESS_DENIED` when `user.tenant_id != tenant_id` for non-SA).

`backend/services/tenant-service/routers/tenants.py` **imports and uses only
`get_db_session` throughout the entire file** — `get_db_session_for_tenant` is never
imported there at all. Every other router that correctly uses
`get_db_session_for_tenant` (`personnel_v2.py`, `positions.py`, `transfer_types.py`)
is safe for exactly this reason. `tenants.py`'s own routes are safe only where an
engineer separately added an explicit `if user.role != "SA": raise 403` inside the
handler body (confirmed present on `update_tenant_plan`, `delete_tenant`,
`suspend_tenant`, `save_tenant_contacts_bulk`, etc.) — `get_tenant`,
`get_approval_rules`, and `put_approval_rules` never got that treatment.

The generic middleware ABAC check in `check_permission()` cannot catch this either:
`require_permission`'s wrapper sets `resource["tenant_id"] = getattr(user,
"tenant_id", None)` — the **caller's own** tenant id — so the mismatch check
`resource["tenant_id"] != user.tenant_id` is a tautology (always False) for every
non-SA caller, regardless of what `{tenant_id}` was in the URL. The path's actual
value is separately captured as `resource["target_tenant_id"]` but is **only ever
used for audit-log attribution**, never compared against anything.

(`outbox` worker's `FOR UPDATE SKIP LOCKED` row-claiming, which is deliberately
tenant-agnostic by design).

## 2. FORCE RLS facts

Tested on a **fresh scratch database** (`smart_scratch_rb1`), `alembic upgrade head`
from empty, independent of `TenantClaude18`'s dev database.

**Every one of the 39 tables with RLS enabled has `relforcerowsecurity = false`.**
No exceptions. (Full list: `adjustment_approval_rules`, `adjustment_orders`,
`approval_rule`, `audit_logs`, `count_sessions`, `dispatch_override_logs`,
`dispatch_strategy_configs`, `inventory_balances`, `lot_allocation_overrides`,
`lot_balances`, `org_node_hierarchy`, `organization_node`, `payment_line_items`,
`payments`, `personnel_positions`, `positions`, `product_approval_minimums`,
`product_brands`, `product_categories`, `product_packaging_types`,
`product_type_codes`, `product_uoms`, `products`, `self_approval_policies`,
`stock_lots`, `subscriptions`, `tenant_addons`, `tenant_hierarchy_config`,
`tenant_renewal_requests`, `terms_acceptances`, `transfer_approval_rules`,
`transfer_discrepancies`, `transfer_line_allocations`, `transfer_orders`,
`transfer_requests`, `transfer_type_config`, `transfer_type_level_permissions`,
`users`, `warehouses`.)

**The far more severe fact: it doesn't matter, because `smart_runtime` — the only
role the application and migrations ever connect as — owns all 56 tables in the
schema.** PostgreSQL does not apply RLS policies to a table's owner unless
`FORCE ROW LEVEL SECURITY` is set, and it is set nowhere. **This means RLS provides
zero protection for the application's actual database connection, full stop —
independent of whether application code remembers to call `set_rls_context()`
correctly.** Proven directly:

```sql
-- as smart_runtime, table owner, two products inserted for two different tenant_ids
-- NO app.current_tenant_id set at all in this session:
SELECT tenant_id, sku, name FROM products;
→ both tenants' rows returned

-- app.current_tenant_id correctly SET to tenant one:
SET app.current_tenant_id = '11111111-...';
SELECT tenant_id, sku, name FROM products;
→ still both tenants' rows returned — the policy is never evaluated for the owner
```

For comparison, a throwaway **non-owner** role (`rb1_nonowner_test`, granted plain
`SELECT`) behaves exactly as the policy text promises:
- `app.current_tenant_id` unset → 0 rows (deny-all, silent).
- `app.current_tenant_id` set to a real tenant id → correctly filtered to 1 row.
- `app.current_tenant_id = ''` (empty string) → **hard error**,
  `invalid input syntax for type uuid: ""` — a 500, not a safe deny. This confirms
  the policy expression itself (`tenant_id = (current_setting('app.current_tenant_id',
  true))::uuid`) is correct and would work as intended *if it were ever evaluated*
  for the role the app actually uses.

**SA code paths and tenant context:** only `inventory-service/dependencies.py` has
an SA-aware `_rls_tenant_for()` helper (SA gets `None`/all-tenants unless it passes
`?tenant_id=`, with a comment explicitly anticipating "tables with FORCE RLS would
cast '' to uuid and 500" for SA — a premise that is currently false, since no table
has FORCE set). `product-service/dependencies.py` and `tenant-service/dependencies.py`'s
plain `get_db_session` call `set_rls_context(session, user.tenant_id, ...)`
unconditionally — for SA, `user.tenant_id` is `None`, with no SA-aware branching at
all in those two services. `tenant-service/dependencies.py`'s separate
`get_db_session_for_tenant` binds RLS context to the **URL's** tenant_id rather than
the caller's, which is safe only because that same function independently 403s on a
tenant mismatch before reaching that line — if RLS were ever actually enforced
(FORCE set, non-owner role), binding context to the attacker-supplied path value
would make RLS trivially bypassable by definition, since the attacker chooses what
tenant the policy filters to.

## 3. RM ABAC facts

**Actions RM holds (per `scripts/seed_permissions.py`'s `"RM"` block) whose
registered ABAC in `registry.py` includes `warehouse_id`:**

`inventory:receive`, `inventory:adjust` (CONDITIONAL), `inventory:cycle_count`,
`inventory:view_balance`, `inventory:issue`, `transfer:dispatch`,
`transfer:receive`, `adjustment:create`, `dispatch:lot_select`,
`report:expiry_alerts`, `count:create_session` — 11 actions total (10 FULL + 1
CONDITIONAL).

**Root cause (static, read directly from code):** `check_permission()` in
`backend/shared/permissions/middleware.py` only applies the node+descendant
warehouse-scope restriction to `FACILITY_SCOPED_ROLES = {"WM", "LM", "SA_GT", "RT"}`.
**`RM` is not a member of that set.** The restriction block is skipped entirely for
RM regardless of the target resource's `warehouse_id`.

**Live confirmation:** created two sibling stock-holding nodes under
`TenantClaude18` ("RB1 Region North", "RB1 Region South"), a real RM position +
user assigned PRIMARY to each (JWT-confirmed `warehouse_id` = own region's node
only), then:

```
GET /api/v1/inventory/lots/expiry-alerts?warehouse_id=<South's node id>
Authorization: Bearer <RM North's token, JWT warehouse_id = North's node>

→ 200 { "success": true,
        "data": { "window_days": 30, "counts": {...}, "items": [] } }
```

`200 OK` — RM North's request for South's `warehouse_id` was **not** rejected with
`ABAC_DENIED: warehouse scope` (the empty `items` reflects that no expiring lots
exist in that fresh node, not a permission denial; a scope-blocked request would
have returned `403`, not `200`). This matches the static finding exactly: today, an
RM can read or write any of the 11 warehouse_id-scoped actions against **any**
warehouse in the tenant, not just their own subtree.

**No verdict is rendered here on whether this is a bug or intended design** — that
question was already raised, deliberately left open, during the Reports-feature
scoping work earlier this session, and stays open for the team.

## Summary

- **3 proven HOLEs** (one read, one write, both exploitable today by any TA against
  any other tenant) traced to a single root cause: `tenants.py` not using the
  router's own designated tenant-isolation dependency.
- **4 additional HOLEs**, all cross-tenant info-leak via unvalidated id fields in
  request bodies (position titles, user full names, product/warehouse names), plus
  one inconsistently-validated FK (`adjustment_orders.warehouse_id`).
- **1 latent hole** (branding upload) not yet exploitable only because no role
  currently holds its permission.
- **RLS is currently providing no protection at all** against any of the above, or
  against anything else, because the application's runtime role owns every table
  and `FORCE ROW LEVEL SECURITY` is set nowhere — a structural fact independent of
  any individual query's correctness.
- **RM's lack of warehouse/node scoping is reconfirmed empirically**, consistent
  with the earlier Reports-feature finding; still an open question for the team, not
  resolved here.
